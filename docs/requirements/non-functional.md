# 非機能要件

機能面は [機能要件](functional.md)、全体像は [プロジェクト概要](../overview.md) を参照。対象 OS は Windows のみ。

## 前提と脅威モデル

このアプリは「ネットワーク越しに本人のデスクトップを完全に操作できる入口」であり、侵害されるとホスト上の全権限が奪われる。以下の信頼境界と脅威を前提に要件を定める。

| 境界 / 脅威 | 前提・対策の方向 |
|------------|----------------|
| tailnet 外からの到達 | tailnet IP のみ Listen（FR-A01。例外は、ChatGPT のサインインの間だけ開く `127.0.0.1` の OAuth コールバック受信口で、NFR-S01・S21。tailnet 公開面ではない）。tailnet ACL で到達元デバイスとポートを絞ることを推奨（NFR-S12） |
| tailnet 内の他デバイス・他ユーザー | WhoIs による許可リスト + MCP は Bearer（FR-A03〜A05） |
| 許可済みデバイスのブラウザ上の悪性ページ（CSRF / DNS リバインディング） | Host / Origin 検証、カスタムヘッダー必須（NFR-S02, S03） |
| AI（MCP クライアント・内蔵エージェント）の暴走 | キルスイッチ、承認、オーバーレイ、監査ログ、**自己保護**（NFR-S06）、タスクの上限（FR-G09） |
| 許可していないプログラムの起動（任意コマンドの実行） | **ホワイトリスト方式（既定）**: `launch_app` は、ホスト所有者がホスト GUI で登録した許可リストのアプリだけを `app_id` で起動する。パス・引数は登録時に固定し、クライアントが指定できない（`path` を渡すと `invalid_argument`。NFR-S20）。許可リスト・起動の方式は MCP・Web UI から書き換えられない。**ブラックリスト方式**（ホスト所有者が GUI の確認モーダルを経て選んだときだけ）: この防御は緩み、`path` で拒否リスト（ホスト GUI だけで登録）に当たらない任意の `.exe` を起動できる。引数は渡せず、固定ディスク上の実体のパスの確認と拒否リストの照合（`app_denied`）を起動のたびに行うが、拒否リストに載せ忘れたプログラム（`cmd.exe`・`powershell.exe` などのインタープリタを含む）と、名前を変えたコピーは止められない。残存リスクはホスト所有者が負う（NFR-S20 の残存リスク） |
| プロンプトインジェクション（画面上の文面でエージェントが乗っ取られる） | **決定論的な多層防御**を主体とする: すべてのアクションを InputGuard・リース・キルスイッチ・ルールベースの Judge（`RuleJudge`）に通し、API の安全チェックと個別操作はホスト承認に回し、上限と中断で被害を限る（NFR-S15）。エージェントへのプロンプト指示は補助にとどめる。高速パスの Jev は自由文を出力せず、アプリが作った不変の候補表から ID を選ぶだけで、承認を緩める方向には一切働かない（NFR-S17）。Jev のプロンプトインジェクション検知には依存しない。**残存リスク（#49）**: 既定の ChatGPT のプラン経路には、OpenAI の API の安全チェック（`pending_safety_checks`。`computer` ツールの機能）が無い。この経路の防御は、InputGuard・RuleJudge・上限・キルスイッチ・承認（Judge が求めたもの・リース承認）・オーバーレイだけで、API キー経路より層が 1 つ少ない（決定事項「ChatGPT のプラン経路の防御の層」） |
| OpenAI API キー・TypeSafe API キー・ChatGPT の OAuth トークンの漏えい | Windows 資格情報マネージャーに保管し、ホスト GUI でのみ登録・削除（ChatGPT はサインイン・解除）する（NFR-S14）。ログ・監査・画面に出さない（NFR-S13）。トークンは `api.openai.com`（Bearer）と `auth.openai.com`（更新・失効）以外へ送らない（NFR-S21） |
| ホストから OpenAI へのデータ送信 | エージェントは既定で無効。有効化時にスクリーンショット送信への同意を記録する。常に `store: false` で送る（FR-G14、FR-G24、NFR-PR03）。接続方式が ChatGPT のプランのときも内容・同意は同じで、ChatGPT のプランの使用量が使われる旨を添える（FR-G14、NFR-PR05） |
| ホストから TypeSafe へのデータ送信 | 高速パスは既定で無効で、エージェントとは別の同意を要する。送るのはテキスト・JSON のみ（ウィンドウタイトルを含み、スクリーンショット・要素の値・入力本文は含まない）。送信先・上限・縮退は NFR-S18、内容は NFR-PR04 |
| ChatGPT へのサインインのコールバック（ホスト上の他プロセス・ブラウザ上の悪性ページ・認可コードの横取り） | `127.0.0.1` だけで Listen する一時的な受信口を、サインインの間（最長 5 分）だけ開く。`state`・`nonce`・PKCE（`S256`）をサインインのたびに新しく作り、`state` が一致した 1 回だけ受け付け、ID トークンを検証し、`sub` の不一致を拒否する（NFR-S21）。同一ユーザー権限の悪意あるプロセスは対象外（NFR-S14 と同じ） |
| ChatGPT のプランの上限到達時の、承認のない API キー経路への課金の付け替え | **自動で切り替えない**。上限・認可切れ・エラーのいずれでも、タスクを止めて API キー経路へ送らない。切り替えられるのはホスト GUI の確認モーダルでの明示的な承認だけ（NFR-S22、FR-G30） |
| ホスト上の他プロセス・他ユーザー | NTFS ACL（NFR-S11）。同一ユーザー権限の悪意あるプロセスは対象外 |
| 更新経路の侵害 | 署名検証（NFR-S10）。公開鍵はバイナリに埋め込み、署名は版・ファイル名に束縛する。リリース CI の侵害（Secret の漏えい）は対象外（鍵は Secret にだけ置き、ログに出さない） |

**HTTP のみで提供する（tailnet の WireGuard に暗号化を委ねる）**。このため Web UI は非セキュアコンテキストで動作し、ブラウザの `navigator.clipboard` が使えない（[機能要件 FR-W07](functional.md) は貼り付けイベントと専用入力欄で実現する）。ホスト GUI（Wails の WebView2。`*.localhost` はセキュアコンテキストとして扱われる）のトークン表示だけは、ユーザーのクリックで `navigator.clipboard.writeText` を使い、使えない場合は全選択 + Ctrl+C の案内にフォールバックする。

## 性能（NFR-P）

測定条件: 1920×1080 のシングルモニター、クライアントとホストが tailnet 上で直接経路（DERP 中継でない）、RTT ≤ 30 ms、ホストは 4 コア以上の一般的な CPU。

| ID | 項目 | 目標 |
|----|------|------|
| NFR-P01 | `screenshot` の処理時間（キャプチャ → 縮小 → エンコード。ネットワークを除く） | ≤ 500 ms |
| NFR-P02 | Web UI のライブ表示（10 fps 時）の表示遅延（ホスト画面の変化 → ブラウザ表示） | ≤ 300 ms |
| NFR-P03 | Web UI の入力遅延（ブラウザ入力 → ホストへ注入完了。ネットワークを除く） | ≤ 50 ms |
| NFR-P04 | アイドル時（接続なし or 閲覧者なし）の CPU 使用率 | ≤ 2 %（WebView2 プロセスを除くアプリ本体） |
| NFR-P05 | キルスイッチ発動から全入力停止・全セッション切断まで | ≤ 1 s。**M1 の実装の既知の制限**: 受付停止（以後のリクエストへの 503）はメモリ上の状態で直ちに効くが、永続化とセッション切断・入力解放（クローザー）はそれぞれ自分の期限（既定 1 s）を持つため、永続化が遅い（遅いディスクなど）と `Trigger` が戻るまで最大 2 × 期限（既定で 2 s）かかり、この 1 s の目標を超えうる。1 s の保証は未解決（[コンポーネント設計 §13.5](../components/overview.md)） |
| NFR-P06 | リース取得要求から承認ダイアログ表示まで | ≤ 1 s |
| NFR-P07 | 同時閲覧者 | 最大 5。エンコードは (モニター, 品質, FPS) の組ごとに 1 回だけ行い共有する |
| NFR-P08 | `run_task` / `get_task` / `cancel_task` の応答（`run_task` は `task_id` を返すまで） | ≤ 1 s（ネットワークを除く）。エージェントの 1 ステップの所要時間は OpenAI の応答時間に依存するため目標を置かず、ステップ数と実行時間の上限（FR-G09）で制御する |
| NFR-P09 | 高速パスの 1 ステップの所要時間（UI Automation の列挙 → TypeSafe への問い合わせ → 入力 → 再観測。ネットワークを除かない） | 暫定 ≤ 2 s。暫定値であり、M4 で固定タスクセットを用いて実測して確定する（仕様書に性能の主張は書かない） |

メモリ使用量・ネットワーク帯域は、実装後に実測してから本書へ追記する方針のため、初版では意図的に目標を置かない（未決事項ではない）。

## セキュリティ（NFR-S）

| ID | 要件 |
|----|------|
| NFR-S01 | tailscaled が持つ tailnet アドレス（IPv4・IPv6）のうち取得できたもののそれぞれに bind して Listen し、`0.0.0.0`・`127.0.0.1`・tailnet 以外のアドレスでは Listen しない（[FR-A01](functional.md)）。片方だけ取得できたらそれだけで動作し、両方とも取得できなければサーバーを停止して GUI に理由を表示する。Listen 対象に変化があれば GUI に表示する。例外は、(1) ビルドタグ `e2e` のテスト専用サーバー（リモートルーターをループバックで Listen する。ホスト側の操作と偽の injector の入力の読み取りのための制御エンドポイントも、loopback の IP リテラルにだけ bind する。[フロントエンド設計](../architecture/frontend.md) §9）で、本番のビルドには含めない（`go build ./...` はタグなしで無視する）、(2) ChatGPT へのサインインの間だけ開く OAuth のコールバックの一時的な受信口（`127.0.0.1` の IP リテラルだけに bind する。tailnet・他のアドレスには出さず、リモートルーター・GUI ルーターとは別物。[FR-G28](functional.md)、NFR-S21）だけ |
| NFR-S02 | すべての HTTP / WebSocket リクエストで `Host` ヘッダーを検証し、tailnet IP または MagicDNS 名 + 設定ポート以外は拒否する（DNS リバインディング対策）。`Origin` ヘッダーを持つリクエスト（ブラウザ）は、同一オリジンのみ許可する |
| NFR-S03 | Web UI の状態変更リクエスト（HTMX のフォーム送信）はカスタムヘッダー `X-Puppet-Remo: 1` を必須とする。このヘッダーはクロスオリジンではプリフライトを要求するため、CORS を許可しない本アプリでは他オリジンのページから送れない。Content-Type は強制しない（HTMX の既定のフォーム形式を使う）。`Origin` 検証（NFR-S02）と併用する。`/api/v1` は GET のみで状態を変更しない。MCP は Bearer 必須のため CSRF の対象外 |
| NFR-S04 | **Bearer トークン**（形式・保存・照合の唯一の定義。他の文書はこれを参照する）: 形式は `prm_` + base64url（パディングなし）でエンコードした 32 バイト（256 bit）の暗号論的乱数（接頭辞を含めて 47 文字）。DB には、接頭辞を含むトークン文字列（UTF-8）の SHA-256 だけを保存する。照合は、提示されたトークン文字列の SHA-256 を計算し、保存済みのハッシュと定数時間で比較する。平文は発行時に一度だけ表示し、保存しない。認証失敗は同一デバイスにつき 1 分 10 回までとし、超過は 429 を返す。認証失敗は監査ログへ DB に追記する（M1。閲覧 UI は M3。[FR-AU01](functional.md)）。ログ・監査ログにトークン（平文・ハッシュとも）は出さない（NFR-S13） |
| NFR-S05 | WhoIs の結果は接続元 IP 単位に最大 10 秒キャッシュする（IP 再割り当て・ノード削除への追従のため短くする）。WhoIs 失敗時は拒否（fail closed）。LocalAPI への WhoIs の 1 回の問い合わせは 5 秒で打ち切り、失敗として扱う（失敗はキャッシュしない） |
| NFR-S06 | **自己保護**: MCP / Web UI / 内蔵エージェントからの入力注入は、アプリ自身のウィンドウ（ホスト GUI、承認ダイアログ）を対象にできない。座標が自ウィンドウ上、またはフォアグラウンドが自プロセスのときは `input_blocked` を返す。ただし操作中オーバーレイ（FR-H07。自プロセスのクリック透過のウィンドウ = `WS_EX_TRANSPARENT` かつ `WS_EX_LAYERED`）は全モニターを覆うが入力を下のウィンドウへ通すので対象外とし、座標の判定は下の実ウィンドウで行う（オーバーレイの下にあるダイアログなどは拒否のまま）。自ウィンドウ（オーバーレイを含む）は画面キャプチャから除外する（`WDA_EXCLUDEFROMCAPTURE`）。これにより AI が承認ダイアログを押す、設定を変える、API キーを入力・参照することを防ぐ。内蔵エージェントでは 1 度でもブロックされたらタスクを終了する（FR-G07）。自ウィンドウは画像に写らないため、AI が避けられるよう、`own_window` のエラー・`screenshot`・`list_windows`・`instructions` で範囲と印を伝える（FR-M20。範囲は縮小座標の矩形だけで、ウィンドウのタイトル・内容は載せず、キャプチャ除外は変えない） |
| NFR-S06（追記。#156） | **スコープ付きのリースの自己保護**: スコープ付きのリース（FR-L09〜L14）でも、自ウィンドウ・昇格ウィンドウは T に選べず（束縛の時点で `own_window` / `elevated_window`）、対象グループ G のメンバーにも入らない（座標の最上位・前面が自ウィンドウ・昇格ウィンドウなら既存の `own_window` / `elevated_window` で停止する）。入力の検証は注入の直前（`lockInput` の中）と複数回の注入の間に行い、通らなければ何も注入せず `ReleaseAll` を呼んでリースを `halted` にする（NFR-S06 の既存の拒否に加えて、PID が同じだけのウィンドウ・別プロセスの子ウィンドウ〔引き上げ前の葉〕・所有関係を確かめられないウィンドウへの入力を止める）。`halted` からの復帰は保持者の明示的な再開だけで、全条件を再検証する。クリップボードはサーバー側の規則で、スコープ付きは書き込みだけ許可し、読み取りは `clipboard_out_of_scope` で拒否する（platform の読み取りは呼ばない）。監査にウィンドウのタイトル・入力した文字は残さない（NFR-S13）。撮れないとき（T・検証できたメンバー）はモニター撮影・画面領域のコピーに切り替えず、`capture_unavailable` / `capture_member_unavailable` で停止する。**この制限は誤入力を止めるガードレールで、セキュリティ境界ではない**（認可済みクライアントの `screenshot`・モニター表示は止めない）。**Windows 実機の検証（成功条件 S1〜S3）は検証環境がなく「検証待ち」で、Windows の `GrabGroup` は未実装のため、実機のスコープ付きのリースは `capture_unavailable` で安全に停止する（完了・合格ではない）** |
| NFR-S07 | キルスイッチの発動状態は永続化し、アプリを再起動しても受付停止のまま維持する。解除はホスト GUI での明示操作のみ |
| NFR-S08 | アプリは標準ユーザー権限で動作し、管理者昇格を要求しない（UIPI により管理者ウィンドウは操作不可。[機能要件](functional.md) 参照） |
| NFR-S09 | リソース上限: HTTP ボディ ≤ 1 MiB（MCP は SDK の `MaxRequestBodyBytes` を 1 MiB に明示設定する。ホスト GUI は状態変更リクエストの本文を `router.GUIMaxBodyBytes` = 1 MiB に制限し、超えたら 413）、HTTP ヘッダー ≤ 64 KiB（`MaxHeaderBytes`）、アイドル接続 120 秒（`IdleTimeout`）、`type` のテキスト ≤ 10,000 文字、クリップボード ≤ 1 MiB、WebSocket メッセージ ≤ 64 KiB、`run_task` の `prompt` ≤ 10,000 文字、最終回答 ≤ 10,000 文字。同期の MCP ツール呼び出しのタイムアウトは 30 秒（`run_task` / `get_task` / `cancel_task` は即時に応答するため影響を受けない）。MCP のセッションは SDK の `SessionTimeout` を **30 分（アイドル）に明示設定する**（既定値 0 はセッションが閉じないため）。リースのアイドル解放（5 分）とは独立した設定である。再開用の `EventStore` は使わない（ストリーム再開なし。クライアントは再初期化する） |
| NFR-S10 | 自動更新は GitHub Releases から HTTPS で取得し、アプリに埋め込んだ公開鍵（Ed25519）で署名を検証してから適用する。署名検証失敗・ダウングレード（現行より古い版）・同じ版は適用しない。署名は minisign 形式（Ed25519）で、インストーラのバイト列全体への署名に、版とファイル名を `version=<版> file=<ファイル名>` として trusted comment に入れる（署名済みの古いインストーラの付け替えを検出する）。公開鍵はリポジトリの `internal/service/updater_pubkey.pub` を `go:embed` し、未設定（プレースホルダ）の間は適用しない（fail closed）。取得に認証情報は使わない（リポジトリは公開が前提。非公開の間は確認が失敗するだけでアプリは止まらない）。署名鍵（秘密鍵）はリポジトリ・ログに置かず、GitHub Actions の Secret（`MINISIGN_SECRET_KEY`）にだけ置く。Secret が無いときは CI は署名を付けず、アプリは署名のないリリースを適用しない |
| NFR-S11 | データ（SQLite、サムネイル、ログ）は `%LOCALAPPDATA%\puppet-remo\` に保存し、NTFS ACL（現在のユーザーのみ）で保護する。**サムネイルは平文**で保存される。残存リスクとして、BitLocker による全体暗号化とサムネイル無効化設定（FR-AU02）を README / 設定画面で案内する。シークレット（OpenAI・TypeSafe の API キー、ChatGPT の OAuth トークン）はここに置かない（NFR-S14） |

に両方を記載する。ホワイトリスト方式（既定）ではブロックリストによる拒否は行わない（所有者の判断に委ねる）。ブラックリスト方式の拒否リストは、起動を許す範囲を所有者が広げたうえで除外を決める仕組みで、安全を保証しない。起動したプロセスのその後の動作は、本アプリの管理外（終了・監視しない） |
| NFR-S21 | **ChatGPT のサインイン（OAuth）の防御**（FR-G28・G29）: (1) **送信先の固定**: ブラウザで開くのは `https://auth.openai.com/api/accounts/authorize`（アプリが組み立てた 1 つ）と、使用量の管理先 `https://chatgpt.com/settings/usage`（使用量の上限の表示・「使用量を管理」。トークンを付けない）だけ。コードの交換・更新は `https://auth.openai.com/api/accounts/oauth/token`、失効は OpenAI の `openid-configuration` の `revocation_endpoint`（`auth.openai.com`）、モデル一覧・推論は `https://api.openai.com/v1` だけ。ChatGPT の `backend-api` は使わない。アクセストークンは `api.openai.com` の `Authorization: Bearer` にだけ付け、URL・クエリ・ログ・エラー文に入れない。リフレッシュトークンは `auth.openai.com` のトークン・失効のエンドポイントにだけ、ID トークンは認可エンドポイントへの `id_token_hint` にだけ送る（`id_token_hint` を含む URL は運用ログ・診断に出さない。NFR-S13）。(2) **コールバックの受信口**: サインインの間だけ、`127.0.0.1` の空きポートに 1 つ開く（`localhost`・他のアドレスでは Listen しない。リモートルーター・GUI ルーターとは別の `http.Server`）。受け付けるのは `GET /auth/callback` だけで、`Host` が `127.0.0.1:<そのポート>` でなければ拒否する。`state` が一致する最初の 1 回の要求だけをサインインの結果として受け取り、受け取ったら閉じる。`state` の不一致・不正な要求には 400 を返して待ちを続ける（5 分で閉じる。他の者が偽の要求を送ってもサインインを失敗させない）。結果の画面は、静的な短い文言（「サインインの結果をアプリに渡しました。このタブを閉じてください」）だけで、コード・`state` を表示せず、外部のリソースを読み込まない。(3) **秘密の値**: `state`・`nonce`・`code_verifier` は暗号論的乱数でサインインのたびに新しく作り、メモリだけに置き、サインインの終了（成功・失敗・中止・タイムアウト）で破棄する。`redirect_uri` は認可の要求とコードの交換で同じ値を使う。(4) **ID トークンの検証**: 署名（OpenAI の公開 JWKS）・`iss`（`https://auth.openai.com`）・`aud`（発行された `client_id`）・`exp`・`nonce` を検証し、検証に失敗したら資格情報を保存しない。再サインインで `sub` が保存済みのアカウントと違えば置き換えない。(5) **更新の直列化**: 同じアカウントの更新は同時に 1 つだけ（回転するリフレッシュトークンを競合させない）。(6) **操作の主体**: サインイン・解除・接続方式の変更は、ホスト GUI（GUI ルーター）だけが開始できる。MCP・Web UI・内蔵エージェントは、これらの開始・トークンの参照・接続方式の変更をできない（リモートルーターに同名の経路を作らない）。(7) **残存リスク**: 同一ユーザー権限の悪意あるプロセスが、サインイン中のポートへ接続する・資格情報マネージャーを読むことは脅威モデル外（PKCE と `state` により、コードだけを横取りしてもトークンには交換できない） |
| NFR-S22 | **接続方式の固定と、API キー経路への切り替えの承認**: タスクの接続方式は開始時に決まり、終了まで変わらない。アプリが ChatGPT のプラン経路から OpenAI API キー経路へ（または逆に）**自動で切り替えることはない**: 使用量の上限（`subscription_sharing_usage_limit_exceeded`）・認可切れ・その他のエラーのいずれでも、API キーが登録済みであっても、止めたタスクを API キー経路で再実行しない。切り替えられるのは、ホスト所有者がホスト GUI の確認モーダルで明示的に承認したときだけ（FR-G30。確定で設定 `agent.connection` を変え、監査する）。承認を省略する経路（設定・MCP・Web UI・エージェントのいずれからも）を作らない。切り替えたあとの新しいタスクだけが API キー経路を使い、止まったタスクは再開されない |

## 可用性・信頼性（NFR-A）

| ID | 要件 |
|----|------|
| NFR-A01 | リースはメモリ上のみで保持し、再起動で必ず `idle` に戻る。リース保持中にアプリが異常終了しても、接続切断によりオーバーレイとリースは消滅する |
| NFR-A02 | クラッシュ後の自動再起動は行わない（安全側）。次回ログオン時の自動起動（FR-S08）で復帰する |
| NFR-A03 | `tailscaled` の再起動・ネットワーク切替後、10 秒以内に Listen を復旧する（[FR-A02](functional.md)）。復旧中のリクエストは接続拒否となる |
| NFR-A04 | クライアントの切断を検知し、当該セッションのリースを解放する。**MCP** は keepalive の ping を**既定で無効**にし（`internal/mcp` の `Config.KeepAlive` = 0）、切断を次で検知する: セッションの明示的な終了（`DELETE`）・トランスポートの切断、SDK の `SessionTimeout`（アイドル 30 分。NFR-S09）、リースのアイドル解放（5 分。[FR-S04](functional.md)）。理由: SDK（go-sdk v1.8.0）のサーバーからの keepalive の ping は standalone の GET SSE ストリームにしか流れず（detached な文脈のリクエストの送り先がそのストリームのため）、GET を張らない（POST だけの）MCP クライアントは ping に応答できない。有効にすると、ツールを呼べている生きたセッションでも、ping の 3 回連続の失敗（`KeepAlive` を有効にしたときの閾値。15 秒間隔で 45 秒。SDK の既定の閾値は 1 回）でセッションとリースを失う。MCP の仕様は GET ストリームを任意としている。**WebSocket**（M2）は、サーバーが 15 秒ごとに ping し、45 秒応答が無ければ切断する |
| NFR-A05 | リース保持中はホストのスリープ・画面消灯を抑止する（`SetThreadExecutionState`）。リース解放で解除する |
| NFR-A06 | SQLite は WAL モードで運用し、起動時に整合性チェックを行う。DB が破損していれば隔離（リネーム）して空 DB で起動し、GUI に通知する |
| NFR-A07 | PC のスリープ・電源オフ中は到達不可（Wake-on-LAN 等は対象外） |
| NFR-A08 | タスクの記録は永続化するが、実行状態はメモリのみで持つ。起動時に、状態が `pending_approval` / `running` のまま残っているタスクを `aborted` に更新する。タスクを自動で再開しない |

### Jev（高速パス）のリスク

- 本設計は Jev のプロンプトインジェクション検知に**一切依存しない**。Jev は自由文を出力せず、アプリが作った固定の候補表から ID を 1 つ選ぶだけである（NFR-S17）。
- Jev は敵対的な内容に弱いとされる（ジャグド・インテリジェンスの資料）。この弱さは、固定の候補表、`RuleJudge`、InputGuard、ステップ上限で軽減する。
- コンピュータ操作の品質に関する根拠は、Cua による小規模な自己報告のテスト（成功 8/9 対 9/9、判断の中央値が 13.6 倍速い）にとどまる。高速パスの品質は、M4 で自前の固定タスクセットを用いて実測して確認する。
